# 챗봇 요청 제한

상태: 2026-09-08 DB 적용 완료. 공용 서버 배포 후 검증 결과는 별도 기록한다.
적용 migration: `20260908033403_chat_rate_limits.sql` (제한 및 정리 작업 포함).

| 범위 | 사용자별 제한 |
|---|---|
| 챗봇 7개 API 전체 | 최근 60초간 60회 |
| 새 답변·미리보기 합산 | 최근 60초간 10회 |
| 성공한 메시지 재전송 | 전체 제한만 차감 |

사용자 ID는 Supabase 인증 후 서버가 결정한다. DB 이벤트와 사용자별 트랜잭션 잠금으로
카운터를 공유하므로 서버 재시작·여러 인스턴스에서 제한이 따로 계산되지 않는다.
새 메시지는 저장 RPC의 소유권·재전송 확인 이후 답변 생성 한도를 차감한다.
이미 저장된 재전송은 답변 생성 한도를 차감하지 않는다.
아직 저장되지 않은 동일 요청이 동시에 들어오면 각 생성 시도가 차감될 수 있다.
생성 실패도 차감하며 인증된 잘못된 요청은 전체 요청 한도를 소비할 수 있다.

## 프론트 처리

한도 초과 시 HTTP 429, Retry-After 헤더와 detail.retry_after(초)를 반환한다.
브라우저는 기존 CORS 설정에서 헤더 접근이 제한될 수 있으므로 JSON 값을 사용한다.

```json
{"detail":{"code":"RATE_LIMITED","message":"잠시 후 다시 시도해 주세요.","fields":null,"retry_after":21}}
```

입력 문구를 보존하고 남은 시간 동안 전송 버튼을 비활성화한다.
저장 요청 재시도에는 같은 client_message_id·본문·채팅방을 사용한다.
DB 장애 시 제한 검사를 생략하지 않고 502 DATA_SOURCE_ERROR로 차단한다.

## 저장·보안

- chat_rate_limit_events는 사용자 ID·요청 범주·시각만 저장하며 질문·답변·토큰은 저장하지 않는다.
- RLS 활성화, anon/authenticated 접근 금지, 서버 service_role만 실행 가능하다.
- 사용자 활동 중 60초 이전 이벤트를 제거한다. 별도 5분 주기 작업은 5분보다 오래된 이벤트를 정리한다.
- 외래키는 추가하지 않는다. 기존 대화 30일 삭제와 별도 작업이다.
- 이 제한은 인증 이후에 적용한다. 미인증 트래픽, 로그인, IP 단위 DDoS 보호를 대체하지 않는다.
- 사용자 수가 늘면 이벤트 테이블·Cron 성능을 관찰해야 한다.

## 검증·배포 순서

1. 격리 SQL 검사 18개, Python 전체 테스트 170개 통과.
2. backend/sql/chat_rate_limits.sql을 migration으로 적용한다.
3. backend/sql/chat_rate_limit_cleanup.sql을 적용한다.
4. 새 백엔드 코드를 커밋·푸시하고 Render에서 수동 배포한다.
5. 합성 계정으로 10회 허용·11회 차단·시간 경과 재허용·동시 요청을 검증한다.

DB SQL이 적용되기 전에 API만 배포하면 챗봇 요청이 502로 차단되므로 순서를 지켜야 한다.
기존 migration 전체를 db push하지 않는다.

## 롤백

문제가 있으면 먼저 API를 이전 배포로 되돌린다. 그 뒤 필요할 때 운영자가
autofit-chat-rate-limit-cleanup 작업만 중단한다. 기존 대화 삭제 작업은 변경하지 않는다.
새 테이블과 함수는 즉시 삭제하지 않고 원인 확인 후 별도 정리한다.
