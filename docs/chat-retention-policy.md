# 챗봇 30일 보관 정책

기준일: 2026-09-08. 사용자 확정: 각 메시지 생성 시각부터 30일.

## 상태

- SQL 적용 및 격리 PostgreSQL 테스트 12개 통과.
- 실제 Supabase 적용 완료. Cron 작업 1번 활성화, 5분 간격.
- migration: 20260908023614, 20260908023656.
- 실제 DB 트랜잭션에서 만료 쌍 삭제·최근 쌍 유지·제목 정리·반복 실행·API 역할 접근 차단을 검증한 뒤 전체 롤백했다.
- 사전 읽기 점검: 전체 메시지 0건, 만료 메시지 0건, pg_cron 미설치.
- 기존 사용자가 작성한 메시지를 읽거나 삭제하지 않았다.

## 삭제 범위

| 항목 | 정책 |
|---|---|
| 기준 | created_at + 720시간 |
| 실행 | 5분 간격 |
| 대상 | public.chat_messages의 만료 행 |
| 상태 | active·archived 모두 적용 |
| 데이터 | 메시지 본문·근거 등 행 전체 삭제 |
| 자동 제목 | 삭제 질문 앞 100자와 일치하면 null |
| 채팅방 | 행·ID·상태 유지 |
| 다른 데이터 | 프로필·건강·운동·식단 유지 |
| 외래키 | 추가하지 않음 |

실행이 정상이면 만료 후 다음 주기에 삭제된다. 30일이 되는 정확한 순간에 삭제되거나
API에서 즉시 숨겨지는 구현은 아니다. 잠긴 채팅방·실패·적체 시 더 늦어질 수 있으므로
Cron 실행 이력과 만료 메시지 수를 확인해야 한다.

질문·답변은 저장 시각이 1마이크로초 다르다. 양쪽이 모두 만료됐을 때 함께 제거하여
재전송 기능이 깨지지 않게 한다. 만료 전 다른 메시지는 삭제하지 않는다.
기존 제목은 자동·수동 구분 컬럼이 없어 삭제 질문 앞 100자와 같은 제목만 비운다.
같은 문구를 사용자가 직접 제목으로 지정했어도 비워질 수 있다.

이 함수는 채팅방별 기존 저장 RPC와 같은 행 잠금을 사용한다. 한 번에 최대 100개 방을 처리하며
사용 중인 방은 다음 주기로 넘긴다. 고아 메시지도 만료된 것만 정리한다.
함수는 별도 스키마의 SECURITY INVOKER이며 API 역할에는 실행 권한을 부여하지 않는다.
스케줄 명령은 60초 statement_timeout을 사용한다.

## 준비 파일

- backend/sql/chat_retention_30_days.sql: 삭제 함수, 실행·스케줄 활성화 없음
- backend/sql/chat_retention_schedule.sql: 적용된 활성화 명령 참조
- backend/tests/chat_retention_sql.mjs: 실제 DB와 격리된 12개 검증

검증: 만료 행 삭제, 새 메시지 유지, 질문·답변 경계 보존, 보관방·고아 메시지 처리,
제목 정리, 채팅방·다른 테이블 유지, 반복 실행, 역할 접근 제한, 외래키 없음.
실제 pg_cron 첫 실행은 2026-09-08 11:40:00 KST에 succeeded로 완료됐다(runid 1).
다중 연결 동시성은 이번 만료 테스트에서 검증하지 않았다.
적용 후 메시지 0건, 만료 0건, 작업 활성, 외래키 0개를 확인했다.
보안 advisor는 기존 INFO 13개·WARN 1개로 변화가 없었다.
기존 [유출 비밀번호 차단 비활성 경고](https://supabase.com/docs/guides/auth/password-security#password-strength-and-leaked-password-protection)는 별도 개선 대상이다.

## 적용 절차

1. 공유 프로젝트에서 삭제 범위와 5분 주기 활성화를 최종 승인받는다.
2. 원격 스키마·함수 이름·Cron 작업 중복을 확인한다.
3. Supabase migration 도구로 적용하고 반환된 실제 버전에 맞춰 파일을 보관한다.
4. 합성 데이터로 만료·미만료 동작을 확인한다. 기존 데이터는 별도 승인 없이 시험 삭제하지 않는다.
5. Cron 활성화와 실행 이력을 확인하고 보안 advisor를 점검한다.

로컬 supabase CLI가 없어 원격 migration에 실제 기록된 버전으로 적용 SQL을 보관했다.
기존 다른 migration 전체를 db push하지 않는다.

## 중단·복구 한계

승인된 운영자가 다음 명령으로 향후 실행을 중단할 수 있다.

```sql
select cron.unschedule('autofit-chat-retention-30-days');
```

중단해도 이미 삭제된 메시지는 앱에서 복구되지 않는다.
Supabase 백업·PITR, Render 로그, 향후 모델 서버나 외부 AI의 로그·보관 데이터는 이 함수의
삭제 범위가 아니다. 별도 보관 정책 확인이 필요하다.
삭제 이후 같은 client_message_id를 다시 보내면 기존 재전송 기록이 없어 새 질문으로 처리될 수 있다.
프론트는 질문별 새 UUID를 생성하고 오래된 질문의 무기한 자동 재시도를 하지 않아야 한다.
